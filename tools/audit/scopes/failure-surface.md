FAILURE-SURFACE AUDIT (template: copy to a scope file outside the output directory and fill the three parts).
A real run of this system exposed a fault. The fault has been or is being fixed where it showed; this audit is NOT a review of that fix. It is a search along the failure surface: every OTHER place in the repository that makes the same assumption and would fail, mislabel or publish a wrong number when the assumption does not hold.

THE ASSUMPTION THAT FAILED (general form): <one or two sentences: what the code assumed about its input, its environment or the provider>.
THE EVIDENCE (real): <what ran, on which dates and build, the exact error or published state, the real provider facts found>.
WHERE IT SHOWED: <file:line of the place that failed, and the commits that fixed it, so that place is not reported again>.

Search method: start from the mechanism, not from the file. Enumerate every reader of the same kind of input (every provider endpoint and every file format the engine ingests; every window that reaches back in time; every place that treats "no data" by a status code, an empty body, a zero, a missing file or a missing directory; every loop where one element's failure returns an error for the whole collection), and for each one say what it does when the assumption fails: FAILS THE DAY, FAILS THE ASSET (contained), MISLABELS (engine fault for a provider condition or the reverse), WRONG NUMBER (a value published from a misread or defaulted input), or HOLDS (handled: say how, file:line). Give for each the trigger in real terms (which dates of the build's range, 2022-05-27 to today, which assets) and whether you confirmed it by reading or only suspect it. Prefer ten confirmed sites to forty guesses; rank by WRONG NUMBER first, then FAILS THE DAY over many dates, then MISLABELS.
